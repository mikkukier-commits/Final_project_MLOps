# 01. Архітектурні рішення (Architectural Decision Records — ADRs)

Цей документ фіксує п'ять ключових архітектурних рішень для гібридної платформи **SupportFlow AI** на AWS (EU та US регіони). Усі рішення узгоджені з бюджетним обмеженням **$120,000/міс ($1,440,000/рік)**, вимогами **EU AI Act / GDPR** та цільовим SLA **99.9%**.

---

## ADR-001: Гібридна стратегія хостингу моделей (Self-Hosted Llama 3.3 70B + Classical ML на AWS EKS з Commercial API Fallback)

- **Статус:** Accepted
- **Дата:** 2027-02-18
- **Особа, що приймає рішення:** Senior AI PM (у консультації з CTO)
- **Проконсультовано з такими Stakeholder'ами:** CTO, Lead MLOps Engineer, ML Lead, CFO, Head of Compliance

### Контекст

SupportFlow AI обробляє **~8M звернень щомісяця** (96M/рік) на 12 мовах для 1,200 enterprise-клієнтів у ЄС та США. Використання 100% комерційного LLM API коштує **$0.024 за тикет** (**$192,000/міс** або **$2,304,000/рік** лише за генерацію без урахування зростання обсягів) і створює ризики передачі персональних даних клієнтів (PII) стороннім провайдерам в умовах GDPR та EU AI Act. Водночас 3 місяці тому помилкова обіцянка моделі призвела до прямих збитків **$23,000** у ключового клієнта (~15% ARR), тому нам потрібен повний контроль над промптами, вагами та відмовостійкістю перед виходом у сегмент білінгу та chargebacks.

### Рішення

Впровадити гібридну модель хостингу на **AWS EKS**: 95% LLM-запитів обробляються fine-tuned **Llama 3.3 70B** на виділеній групі GPU-нод (`g5.2xlarge` із рушієм vLLM/TorchServe), класичні ML-моделі (Intent Classifier на 25 категорій, пріоритизація, sentiment) працюють на CPU-нодах (`m6i.xlarge`), а для <5% надскладних або пікових запитів працює керований fallback на комерційний API із попередньою маскованою санітизацією PII.

### Розглянуті Альтернтативи

#### Альтернтатива 1: 100% Commercial LLM API (OpenAI / Anthropic)

- **Опис:** Надсилання всіх 8M звернень на місяць до зовнішнього керованого API без власної GPU-інфраструктури.
- **Плюси:** Мінімальний CAPEX (~$50K на інтеграцію), нульове навантаження на підтримку GPU-кластера, швидкий старт (2–3 тижні).
- **Мінуси:** Неконтрольоване зростання OPEX при масштабуванні, передача чутливих контекстів третім сторонам, залежність від лімітів зовнішнього провайдера, неможливість глибокого fine-tuning на закритих історичних тикетах.
- **Оцінюваний вплив на вартість:** **$2,304,000/рік** при 8M/міс ($0.024/тикет) і **$3,456,000/рік** при 12M/міс — на **$864,000/рік** дорожче вже в 1-й рік.
- **Чому не обрано:** Знищує маржинальність при зростанні до 10–16M звернень/міс і блокує проходження enterprise-комплаєнсу в ЄС.

#### Альтернтатива 2: 100% Self-Hosted LLM на EKS без комерційного fallback

- **Опис:** Обробка 100% запитів, включно з піковими сплесками та рідкісними edge-cases, виключно на власних GPU-нодах.
- **Плюси:** Нульова залежність від зовнішніх API-провайдерів, максимальна ізоляція даних.
- **Мінуси:** Вимагає тримати подвійний резерв GPU-потужностей (зайві +4 ноди `g5.2xlarge` простоюють 85% часу) для покриття пікових навантажень у Чорну п'ятницю та високий ризик відмов при дефіциті GPU в AWS регіоні.
- **Оцінюваний вплив на вартість:** Додає **+$28,000/міс (+$336,000/рік)** за резервні GPU проти $10,000/міс бюджету на <5% API fallback.
- **Чому не обрано:** Економічно неефективно тримати надлишкові GPU для <5% пікового навантаження.

#### Альтернтатива 3: AWS Bedrock Managed Hosting (Fine-tuned моделі в межах VPC)

- **Опис:** Оренда керованого інференсу через AWS Bedrock із private endpoints.
- **Плюси:** Залишається в периметрі AWS, менше операційного навантаження на MLOps (-0.5 FTE).
- **Мінуси:** Вища вартість per-token / provisioned throughput для 70B-моделей при постійному завантаженні 8M+ запитів, обмежена гнучкість кастомних NeMo Guardrails і vLLM-батчингу.
- **Оцінюваний вплив на вартість:** **~$165,000/міс ($1,980,000/рік)** на provisioned throughput — на **$540,000/рік** дорожче за наш EKS-кластер.
- **Чому не обрано:** Перевищує цільовий бюджет $120K/міс і знижує гнучкість контролю інференс-стеку.

### Наслідки

- **Позитивні:**
  - Пряма економія **$864,000 у 1-й рік** порівняно з 100% Commercial API ($1,440K OPEX vs $2,304K API) та зниження цільової юніт-вартості з **$0.024** до **$0.015** (при 8M/міс) і **$0.012** (при масштабі 10M+/міс).
  - Повний контроль над вагами моделей, PII-периметром та версіонуванням для аудиту EU AI Act.
- **Негативні:**
  - Додає **1.5 FTE MLOps** та **0.5 FTE ML/DS** операційного навантаження (**$420,000/рік**).
  - Ефект «холодного старту» (cold-start) при автоскейлінгу нових GPU-подів (3–5 хвилин до готовності при різких стрибках трафіку).
- **Ризики:**
  - Дефіцит інстансів `g5.2xlarge` у регіоні `eu-central-1` — план Б: failover на `us-east-1` із додатковою мережевою затримкою ~85ms або тимчасове розширення commercial fallback.
  - При падінні трафіку нижче точки беззбитковості (**4.33M тикетів/міс**) self-hosted рішення стає дорожчим за API (перегляд ADR у Q4).

### Показники успіху

- Через 6 місяців: blended unit cost ≤ **$0.015/тикет** (при 8M/міс) із трендом до **$0.012**, `p95 latency < 1.8s`, доступність інференсу ≥ **99.9%**, частка fallback API ≤ **5%**.

### Відношення

- ADR-002, ADR-004, ADR-005
- Threat Model risks: T-001, T-004, T-014, T-015

## ADR-002: Патерн розгортання та відкатів (Progressive Canary Deployments через Argo Rollouts)

- **Статус:** Accepted
- **Дата:** 2026-02-19
- **Особа, що приймає рішення:** Senior AI PM (у консультації з Lead MLOps Engineer)
- **Проконсультовано з такими Stakeholder'ами:** CTO, VP Engineering, Lead MLOps Engineer, Head of Support

### Контекст

Згідно з аналізом GitOps (ДЗ 3), статус `Synced` в Argo CD не гарантує, що нова модель видає коректні прогнози. Після фінансового інциденту на $23K будь-який некоректний реліз LLM-адаптера або класифікатора намірів одночасно на 100% із 1,200 клієнтів загрожує масовими галюцинаціями та зривом SLA.

### Рішення

Використовувати **Argo Rollouts** для прогресивного **Canary-розгортання** всіх моделей (як LLM, так і класичного ML): **5% трафіку (15 хв) → 25% трафіку (30 хв) → 100% трафіку**, з автоматичним відкатом за **30 секунд** при порушенні Prometheus AnalysisTemplate (`5xx > 1%`, `p95 latency > 1.8s` або `mlflow_accuracy < 0.90`).

### Розглянуті Альтернативи

#### Альтернатива 1: Blue-Green Deployment (повне перемикання)

- **Опис:** Підняття повної копії prod-середовища (Green) і миттєве перемикання 100% трафіку після smoke-тестів.
- **Плюси:** Просте миттєве перемикання, швидкий ручний rollback назад на Blue.
- **Мінуси:** При перемиканні 100% трафіку дрейф або прихована галюцинація вражає всіх 1,200 клієнтів одночасно; утримання 2× GPU-кластера під час релізу коштує дорого.
- **Оцінюваний вплив на вартість:** Потрібно +100% GPU-буфера на вікно релізу (**+$6,500/міс** додаткових резервних GPU-годин).
- **Чому не обрано:** Занадто високий blast radius (100% клієнтів) та надлишкова вартість подвійного GPU-стеку.

#### Альтернатива 2: Стандартний Kubernetes Rolling Update

- **Опис:** Поступова заміна подів без керування вагою трафіку на рівні Ingress та без автоматичного ML-аналізу метрик.
- **Плюси:** Вбудований у базовий Kubernetes, нульова додаткова складність налаштування.
- **Мінуси:** Немає прив'язки до якості ML-метрик (accuracy, hallucination rate) чи автоматичного відкату; складно ізолювати проблемну версію під час релізу.
- **Оцінюваний вплив на вартість:** $0 прямих витрат на інструмент, але потенційний збиток **>$100K/інцидент** при масовому викочуванні дефектної моделі.
- **Чому не обрано:** Не відповідає вимогам безпеки для high-stakes сценаріїв (billing, chargebacks).

#### Альтернатива 3: Статичний A/B роутинг або Shadow-тестування без авто-промоушену

- **Опис:** Дублювання продакшн-трафіку на нову модель у фоні (shadow) перед ручним перемиканням.
- **Плюси:** Нульовий ризик для користувача під час shadow-фази.
- **Мінуси:** Подвоює обчислювальне навантаження GPU для shadow LLM (фактично 2× GPU-кошт на тестуванні) та вимагає ручного аналізу результатів без швидкої детермінованої ескалації.
- **Оцінюваний вплив на вартість:** **+$18,000/міс** на подвійне GPU-навантаження при shadow-інференсі.
- **Чому не обрано:** Занадто дорого для 70B LLM-моделі; shadow використовується лише точково для нових класів намірів у Staging.

### Наслідки

- **Позитивне:**
  - Обмеження зони ураження дефектного релізу максимум **5% трафіку** і автоматична зупинка деградації за **30 секунд**.
  - Прозорий аудит кожного релізу через Git-коміти в Argo CD та AnalysisRuns.
- **Негативне:**
  - Складніша конфігурація Ingress/Gateway (ALB/NGINX weighted routing) та довший час повного викочування релізу (~45–60 хвилин замість 5 хвилин).
  - Необхідність підтримувати 2 активні версії під час canary-вікна (+15% тимчасового буфера ресурсів).
- **Ризики:**
  - Помилкові спрацювання авто-відкату через тимчасові збої експортера метрик (аналогічно розриву о 08:34 UTC із ДЗ 4) — пом'якшується вимогою 2 послідовних інтервалів деградації перед тригером.

### Показники успіху

- 100% production-релізів проходять через Canary; середній час виявлення й відкату дефектного релізу ≤ **60 секунд**; 0 інцидентів рівня P1, спричинених релізом моделі.

### Відношення

- ADR-001, ADR-003, ADR-004
- Threat Model risks: T-005, T-013

## ADR-003: Стратегія Model Registry та аудиту походження (Self-Hosted MLflow Registry на AWS EKS + S3 Object Lock)

- **Статус:** Accepted
- **Дата:** 2026-02-20
- **Особа, що приймає рішення:** Senior AI PM (у консультації з ML Lead та Head of Compliance)
- **Проконсультовано з такими Stakeholder'ами:** ML Lead, Lead MLOps Engineer, Head of Compliance (DPO), CTO

### Контекст

Для відповідності **EU AI Act (Стаття 11 та 12)** компанія зобов'язана забезпечити 12-місячну незмінну відстежуваність (lineage) від сирих тренувальних даних (12M рядків) і Git-комітів до кожної версії моделі в продакшені. У ДЗ 4 та ДЗ 5 ми вже виявили, що відсутність зафіксованих `run_id` і сплутання статусів `candidate` із `production` блокують безпечний реліз.

### Рішення

Розгорнути централізований **MLflow Tracking & Model Registry** у namespace `prod-ml` на AWS EKS із метаданими в **PostgreSQL RDS** (Multi-AZ), зберіганням артефактів/ваг у **AWS S3 з активованим Object Lock** (12 місяців retention) та жорстким життєвим циклом тегів (`Candidate → Staging-Validated → Approved-for-Prod`), інтегрованим із AWS Step Functions (ДЗ 5).

### Розглянуті Альтернативи

#### Альтернатива 1: AWS SageMaker Model Registry

- **Опис:** Використання повністю керованого реєстру моделей у екосистемі AWS SageMaker.
- **Плюси:** Вбудована IAM-інтеграція з AWS, безкоштовний UI-реєстр, нульове обслуговування сервера реєстру.
- **Мінуси:** Слабка сумісність із поточним стеком експериментів команди на базі MLflow (ДЗ 4) та кастомними LLM evaluation-треками, жорсткий vendor lock-in на SageMaker Pipelines замість гнучкого EKS + Step Functions.
- **Оцінюваний вплив на вартість:** Близько **$3,000/міс** на пов'язані SageMaker-ресурси + витрати на міграцію (~$40K разово і +3 тижні затримки).
- **Чому не обрано:** Команда вже має стандартизовані процеси на MLflow (ДЗ 4–5), а переїзд затримає реліз на 3 тижні.

#### Альтернатива 2: Git LFS + DVC без виділеного Model Registry

- **Опис:** Зберігання метрик у Markdown/JSON файлах Git-репозиторію та ваг через DVC у S3.
- **Плюси:** Мінімальні витрати інфраструктури (~$400/міс лише на S3).
- **Мінуси:** Немає візуального порівняння прогонів, немає API для перевірки stage-статусів у Argo Rollouts / Step Functions, високий ризик людської помилки та відсутність зручного аудиту для регулятора.
- **Оцінюваний вплив на вартість:** Економія ~$1,800/міс на RDS/EKS, але ризик зриву аудиту EU AI Act (штраф до €35M).
- **Чому не обрано:** Неприйнятно для комплаєнсу та щоденної роботи 5 ML-інженерів.

#### Альтернатива 3: Weights & Biases (W&B) Enterprise SaaS

- **Опис:** Перенесення експеримент-трекінгу та реєстру на комерційну хмарну платформу W&B.
- **Плюси:** Багатий інтерфейс для LLM-трейсів і промптів, мінімальний супровід з боку MLOps.
- **Мінуси:** Значна вартість ліцензій per-seat і per-tracked-hour ($4,500–$6,000/міс), передача метаданих експериментів за межі AWS VPC.
- **Оцінюваний вплив на вартість:** **$60,000–$72,000/рік** додаткових ліцензійних витрат проти ~$18,000/рік за self-hosted MLflow на RDS/S3.
- **Чому не обрано:** Вища вартість і гірший контроль локалізації метаданих у ЄС.

### Наслідки

- **Позитивне:**
  - 100% моделей у продакшені мають незмінний lineage: `Git Commit SHA → DVC Dataset Hash → Step Functions ARN → MLflow Run ID → S3 Artifact`.
  - Автоматичне блокування деплою моделей без статусу `Approved-for-Prod` (перевіряється в CI/CD).
- **Негативне:**
  - Необхідність адміністрування RDS, оновлення MLflow та налаштування S3 Lifecycle/Object Lock (~0.15 FTE MLOps).
- **Ризики:**
  - Неконтрольоване зростання S3-сховища через ваги Llama 3.3 (~140 GB на чекпоїнт) — пом'якшується зберіганням у продакшн-S3 лише LoRA-адаптерів та архівацією проміжних чекпоїнтів через 90 днів (зберігаючи метадані та prod-артефакти 12+ місяців).

### Показники успіху

- **100%** prod-моделей мають повний audit trail у MLflow + S3 Object Lock; час підготовки звіту для комплаєнс-аудиту < **4 годин**.

### Відношення

- ADR-001, ADR-002, ADR-004
- Threat Model risks: T-010, T-012, T-013

## ADR-004: Стек спостережуваності та аудиту (Prometheus + Grafana + Loki + OpenTelemetry + S3 Archive)

- **Статус:** Accepted
- **Дата:** 2026-02-21
- **Особа, що приймає рішення:** Senior AI PM (у консультації з Lead MLOps Engineer)
- **Проконсультовано з такими Stakeholder'ами:** CTO, Lead MLOps Engineer, Head of Support, Head of Compliance

### Контекст

SupportFlow AI повинен одночасно контролювати системні метрики EKS/GPU (latency, OOM, VRAM), класичний ML drift (`mlflow_accuracy`, `mlflow_loss`, PSI), а також якість і безпеку LLM/RAG (спрацювання NeMo Guardrails, hallucination score, cosine similarity). При цьому всі рішення про бюджет вимагають утримання інструментарію в рамках **$120,000/міс** загального OPEX.

### Рішення

Використовувати комбінований open-source стек на EKS: **Prometheus** (збір системних і MLflow-метрик), **Grafana** (3 дашборди для інженерів, безпеки та менеджменту), **Loki + OpenTelemetry** (структуровані логи та трейси запитів із маскуванням PII), інтегрований із **PagerDuty/Slack** для алертингу та довготривалою архівацією промпт-хешів у **S3 Object Lock**.

### Розглянуті Альтернативи

#### Альтернатива 1: Повний комерційний стек Datadog (APM + Logs + LLM Observability)

- **Опис:** Використання SaaS-платформи Datadog для інфраструктури, логів, трасування та LLM-метрик.
- **Плюси:** Єдине вікно з коробки, готовий модуль LLM Observability, економія часу MLOps на підтримці.
- **Мінуси:** Надзвичайно висока вартість на масштабі 8M запитів/міс (плата за кожен хост, GB логів та спан OpenTelemetry); дані логів залишають AWS VPC.
- **Оцінюваний вплив на вартість:** **$18,000–$26,000/міс ($216K–$312K/рік)** лише за Datadog (перевищує весь наш бюджет на інструменти й моніторинг у 2–3 рази).
- **Чому не обрано:** Неприпустимо висока вартість при зростанні до 16M запитів/міс.

#### Альтернатива 2: Нативний AWS CloudWatch + X-Ray

- **Опис:** Стандартні метрики та логи AWS без розгортання Prometheus/Loki.
- **Плюси:** Мінімальне налаштування EKS-агентів.
- **Мінуси:** Високі витрати на інгест логів при великих обсягах ($0.50/GB), слабка підтримка PromQL для складних Canary AnalysisTemplates в Argo Rollouts та обмежена візуалізація ML-метрик.
- **Оцінюваний вплив на вартість:** **~$7,500–$10,000/міс** із незручною інтеграцією під MLflow і Argo Rollouts.
- **Чому не обрано:** Гірша інтеграція з GitOps/Argo Rollouts (ADR-002) і відсутність стандартизованих ML-експортерів із ДЗ 4.

#### Альтернатива 3: Спеціалізована SaaS-платформа ML Observability (Arize AI / WhyLabs) у зв'язці з базовим CloudWatch

- **Опис:** Винесення аналітики дрейфу і LLM-evals у сторонній SaaS.
- **Плюси:** Просунуті готові візуалізації дрейфу ембедингів та галюцинацій.
- **Мінуси:** Додаткова підписка $3,500–$5,000/міс і передача даних інференсу на зовнішній SaaS, що ускладнює GDPR Data Processing Agreements із клієнтами.
- **Оцінюваний вплив на вартість:** **+$54,000/рік** додатково до інфраструктурного моніторингу.
- **Чому не обрано:** Дорогий дублюючий контур із додатковими GDPR-ризиками.

### Наслідки

- **Позитивне:**
  - Утримання витрат на моніторинг, алертинг і безпекові ліцензії в межах **$10,000/міс** (разом із PagerDuty та сканерами — $120K/рік у рядку Tools & licensing).
  - Нативна інтеграція Prometheus із Argo Rollouts (авто-відкат за 30 сек) та 100% збереження даних усередині AWS VPC.
- **Негативне:**
  - Потребує ~0.25 FTE MLOps на підтримку retention-політик Loki/Prometheus та налаштування кастомних експортерів.
- **Ризики:**
  - Збій або перезапуск Prometheus exporter (як у кейсі ДЗ 4 о 08:34 UTC) може створювати сліпі зони — пом'якшується high-availability реплікацією Prometheus (`replicas: 2`) та алертами `TargetDown`.

### Показники успіху

- Виявлення дрейфу точності (`mlflow_accuracy < 0.90`) або PII-аномалій ≤ **5 хвилин**; 100% P1-інцидентів зафіксовані зі збереженим трейсом для постмортему.

### Відношення

- ADR-002, ADR-003
- Threat Model risks: T-005, T-010, T-012, T-013

## ADR-005: Архітектура векторного сховища для RAG (Pinecone Enterprise з жорсткою Namespace-ізоляцією)

- **Статус:** Accepted
- **Дата:** 2026-02-22
- **Особа, що приймає рішення:** Senior AI PM (у консультації з CTO та Head of Compliance)
- **Проконсультовано з такими Stakeholder'ами:** CTO, Backend Lead, ML Lead, Head of Compliance (DPO), CFO

### Контекст

RAG-контур SupportFlow AI обслуговує **~3.5M векторів** із баз знань 1,200 enterprise-клієнтів (каталоги товарів, політики повернення, FAQ) із вимогами пошуку Top-K контексту за `< 80ms` на 12 мовах. Найбільший продуктовий та юридичний ризик — **крос-тенантний витік (Cross-Tenant Leakage)**, коли клієнт A бачить конфіденційні умови клієнта B.

### Рішення

Використовувати керований **Pinecone Enterprise** (окремі виділені поди в межах AWS EU/US регіонів) із примусовою ізоляцією кожного клієнта через `namespace = tenant_id`, який інжектується на рівні API Gateway виключно з підписаного JWT-токена (ніколи з payload користувача), та щоденним бекапуванням індексів у S3.

### Розглянуті Альтернативи

#### Альтернатива 1: PostgreSQL + `pgvector` на Amazon RDS

- **Опис:** Зберігання 3.5M векторів у наявній реляційній БД PostgreSQL із розширенням `pgvector` і Row-Level Security (RLS).
- **Плюси:** Немає нового вендора; спільні SQL-транзакції для метаданих і векторів; нижчий стартовий чек (~$2,500–$3,500/міс).
- **Мінуси:** При зростанні до 10M+ векторів і 1,200+ паралельних фільтрацій за `tenant_id` індекси HNSW у PostgreSQL деградують за latency (p95 зростає >250ms) та вимагають складного шардингу вручну.
- **Оцінюваний вплив на вартість:** Економія ~$5,000/міс на старті, але +0.5 FTE Backend/DBA на оптимізацію шардингу (**+$90,000/рік**) та ризик порушення SLA `< 1.8s`.
- **Чому не обрано:** Погано масштабується для мультиарендного пошуку з фільтрацією на 8M–16M запитів/міс.

#### Альтернатива 2: Self-Hosted Weaviate або Qdrant на AWS EKS

- **Опис:** Розгортання open-source векторної БД безпосередньо в нашому EKS-кластері (`prod-rag`).
- **Плюси:** Повний контроль усередині VPC, відсутність плати вендору за SaaS-хостинг (лише EC2/EBS ~$4,000/міс).
- **Мінуси:** Значне операційне навантаження на команду (2 MLOps уже перевантажені GPU-стеком і MLflow), високий ризик втрати консистентності індексів чи тривалого відновлення після збоїв нод.
- **Оцінюваний вплив на вартість:** Економія ~$4,500/міс на інфраструктурі, але потребує додатково +0.5–1.0 FTE інженера (**+$100K–$180K/рік**).
- **Чому не обрано:** Команда з 2 MLOps не має ресурсу безпечно підтримувати stateful розподілену векторну БД у production.

#### Альтернатива 3: Amazon OpenSearch Serverless (Vector Engine)

- **Опис:** Використання керованого векторного пошуку AWS OpenSearch.
- **Плюси:** Повна нативність у AWS IAM, відсутність зовнішнього контракту, гарний гібридний повнотекстовий + векторний пошук.
- **Мінуси:** Мінімальна вартість OCU-потужностей для низької затримки та 1,200 ізольованих колекцій/фільтрів суттєво дорожча і має повільніший cold-scale при сплесках.
- **Оцінюваний вплив на вартість:** **~$11,000–$14,000/міс** на high-availability OCU-кластер.
- **Чому не обрано:** Дорожче й складніше в керуванні 1,200 тенантами, ніж namespace-механізм Pinecone.

### Наслідки

- **Позитивне:**
  - Стабільна затримка векторного пошуку `p95 < 65ms` навіть при масштабуванні з 3.5M до 10M векторів.
  - Чітка логічна ізоляція `namespace = tenant_id` із можливістю миттєвого видалення даних клієнта («Right to be Forgotten» за GDPR).
- **Негативне:**
  - Залежність від зовнішнього керованого сервісу Pinecone і витрати в межах **$8,500/міс** ($102,000/рік у складі категорії Storage $180K/рік разом із S3/RDS).
- **Ризики:**
  - Помилка в коді API Gateway при мапінгу `tenant_id` (крос-тенантний витік `T-002`) — пом'якшується обов'язковим інтеграційним CI/CD-тестом на 0 перетинів між Tenant_A та Tenant_B перед кожним релізом.

### Показники успіху

- `0` крос-тенантних витоків даних; точність вибору контексту (`Cosine precision @ Top-3`) ≥ **0.85**; `p95` retrieval latency < **80ms**.

### Відношення

- ADR-001, ADR-004
- Threat Model risks: T-002, T-003, T-008
