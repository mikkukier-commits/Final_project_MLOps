# 02. Модель загроз та аналіз ризиків (Threat Model & Risk Matrix)

## 1. Огляд поверхні атак (Attack Surface Narrative)

Платформа **SupportFlow AI** функціонує як мультиарендний B2B SaaS-сервіс для 1,200 корпоративних клієнтів у юрисдикціях **ЄС (GDPR, EU AI Act)** та **США**, обробляючи **8M клієнтських звернень щомісяця** через гібридну архітектуру на **AWS** (EKS, S3, RDS, Step Functions, Pinecone Enterprise). Розуміння меж довіри (trust boundaries) та векторів доступу є критичним після інциденту тримісячної давнини ($23,000 прямих збитків через помилкове фінансове зобов'язання LLM), особливо напередодні виходу продукту в сегмент high-stakes операцій (білінг і оскарження платежів — chargebacks).

### Межі системи та потоки даних (System Boundaries & Data Flows)
Архітектура системи поділяється на чотири ключові зони довіри:

1. **Периметр клієнтського входу (Public / Edge Boundary):** Кінцеві покупці e-commerce брендів та оператори підтримки взаємодіють із системою через віджет чату, email-шлюз або REST/gRPC API. Усі вхідні запити проходять через **AWS CloudFront + WAF** та **API Gateway**, де здійснюється автентифікація за підписаним **JWT-токеном** (що містить `tenant_id` клієнта) та первинна фільтрація через **NeMo Guardrails**. Саме тут виникає перший критичний ризик — користувацький текст містить неперевірені інструкції (Direct Prompt Injection) та персональні дані покупців (імена, адреси, номери замовлень, платіжні деталі).
2. **Контур гібридного інференсу та RAG (Compute & Knowledge Boundary — AWS EKS + Pinecone):** Запит потрапляє у виділений production-кластер EKS, розділений на ізольовані простори імен (`prod-ml`, `prod-llm`, `prod-rag`). Спочатку легка класична ML-модель (Intent Classifier на CPU-нодах `m6i.xlarge`) визначає категорію звернення (25 класів), пріоритет (P1/P2/P3) та тональність. Далі сервіс RAG робить запит до **Pinecone Enterprise** (~3.5M векторів), де суворо передається `namespace = tenant_id` із JWT-токена. Відібрані фрагменти бази знань клієнта формують контекст промпту для **fine-tuned Llama 3.3 70B** на GPU-нодах (`g5.2xlarge`) або, у <5% випадків сплесків/складних кейсів, передаються через TLS 1.3 до комерційного LLM API після обов'язкового знеособлення PII (Presidio). Межа між `prod-rag` і Pinecone є найчутливішою зоною щодо **крос-тенантних витоків даних**.
3. **Контур даних, тренування та реєстру (Data & Supply Chain Boundary):** Історичні діалоги (~12M рядків) проходять через **GitLab CI + AWS Step Functions**, де очищуються від PII та проходять валідацію схеми перед донавчанням. Навчені артефакти та LoRA-адаптери зберігаються в **MLflow Registry** (`prod-ml`) із бекендом у **PostgreSQL RDS** та **AWS S3 Object Lock** (незмінне зберігання 12 місяців для EU AI Act). Вразливість у цьому контурі (скомпрометовані open-source ваги, отруєний тренувальний датасет або надмірні права доступу до MLflow) може скомпрометувати одразу всіх 1,200 клієнтів.
4. **Контур адміністрування, GitOps та спостережуваності (Control Plane Boundary):** Розробники (5 ML, 3 backend) та 2 MLOps-інженери керують кодом через GitLab і розгортають зміни через **Argo CD / Argo Rollouts** (Canary 5% → 25% → 100%). Логи та телеметрія збираються в **Prometheus, Grafana, Loki та OpenTelemetry** з архівацією хешів промптів/відповідей у S3. Якщо в логах OpenTelemetry або Prometheus опиниться незнеособлений PII, або якщо розробник зможе обійти protected branch у GitLab, система втратить як технічну безпеку, так і відповідність GDPR.

### Актори та рівні доступу
* **Зовнішні кінцеві користувачі (Shoppers / Attackers):** Недовірені актори; мають доступ лише до публічного API чату. Можуть навмисно вводити jailbreak-промпти, атакувати API для витягування ваг/логіки або намагатися отримати дані інших покупців.
* **Адміністратори клієнтів-брендів (Tenant Admins):** Довірені лише в межах свого `tenant_id`; завантажують документи в базу знань (джерело ризику Indirect Prompt Injection через заражені HTML/PDF-файли).
* **Оператори підтримки клієнтів (Support Agents):** Переглядають pre-drafted відповіді та можуть схвалювати або коригувати рішення (Human-in-the-loop для high-stakes запитів).
* **Внутрішні інженери (ML / Backend / MLOps):** Мають рольовий доступ (RBAC): розробники обмежені `dev`/`staging`, доступ до `prod` EKS, MLflow `Approved-for-Prod` і S3 Audit мають лише уповноважені MLOps/Release Approvers.

## 2. Методологія пріоритизації (Матриця 3×3: Impact × Likelihood)

Для об'єктивної оцінки загроз використовується матриця **3×3**, де рівень пріоритету розраховується як добуток очікуваного бізнес-впливу та ймовірності реалізації протягом 12 місяців:

* **Impact (Фінансовий та комплаєнс-вплив):**
  * **High (3):** Збиток **> $100,000** за інцидент або на рік, втрата enterprise-контрактів (> $150K ARR), системна зупинка сервісу чи штраф регулятора (GDPR / EU AI Act до €35M або 7% обороту).
  * **Medium (2):** Збиток **$25,000 – $100,000**, локальна деградація якості, перевитрата хмарного бюджету або втрата 1–3 середніх клієнтів ($18K–$54K ARR).
  * **Low (1):** Збиток **< $25,000**, некритичні затримки або тимчасові збої внутрішніх інструментів без впливу на кінцевих користувачів.
* **Likelihood (Ймовірність за 12 місяців):** **High (3)** (>50% на рік), **Medium (2)** (10–50% на рік), **Low (1)** (<10% на рік).

| Ймовірність \ Вплив | Low Impact (1) | Medium Impact (2) | High Impact (3) |
| :--- | :--- | :--- | :--- |
| **High Likelihood (3)** | P3 (`T-015`) | **P2** (`T-005`, `T-014`) | **P1** (`T-001`, `T-004`, `T-006`) |
| **Medium Likelihood (2)** | P3 (`T-008`) | **P2** (`T-003`, `T-007`, `T-009`, `T-016`) | **P1** (`T-002`, `T-010`, `T-012`) |
| **Low Likelihood (1)** | **P3 (Accepted)** (`T-011`) | P3 (`T-013`) | **P2** (`T-010` після контролю) / P2 |

*Примітка: Загрози з оцінкою 6–9 отримують пріоритет **P1** (обов'язковий блокер релізу), 3–4 — **P2** (контрольований план впровадження), 1–2 — **P3** (плановий контроль або усвідомлено прийнятий ризик).*

## 4. Взаємозв'язок загроз із релізним контролем та реагуванням на інциденти

Усі загрози пріоритету **P1** та ключові **P2** безпосередньо інтегровані в операційні процеси команди:
* **Превентивний контроль (`03_Release_Checklist.md`):** Кожен реліз блокується (`Blocker if failed: Yes`), якщо не пройдено тести NeMo Guardrails (`T-001`, `T-006`), тест крос-тенантного розділення Pinecone (`T-002`), бенчмарк галюцинацій `< 0.5%` (`T-004`), сканування PII Presidio (`T-007`), аудит-логування в S3 Object Lock (`T-010`) або перевірку вразливостей Trivy (`T-012`).
* **Реактивний контроль (`04_Incident_Runbook.md`):** Реалізація загрози `T-005` активує **Сценарій 1 (Model Quality Degradation)**, виявлення `T-001`, `T-002` або `T-004` запускає **Сценарій 2 (Critical LLM Security & Compliance Incident із 72-год циклом GDPR)**, а спрацювання `T-013` або `T-016` — **Сценарій 3 (Deployment / Infrastructure Failure)**.
* **Усвідомлено прийняті ризики (`Accepted risk`):** Ризики `T-011` (незначний дисбаланс точності на 2 рідкісних мовах із <1% трафіку) та `T-015` (спроба екстракції класифікатора без витоку даних) задокументовані як прийняті на 12-місячний горизонт із щоквартальним переглядом, що дозволяє сфокусувати бюджет інженерії на P1-блокерах.
